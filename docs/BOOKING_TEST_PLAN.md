# Autumn Nails Booking System — v1 Test Plan

This document is the pre-launch verification checklist for the Autumn Nails online booking system. It is intentionally separate from the customer-facing site.

## 1. Customer journey

- [ ] Booking page loads on desktop.
- [ ] Booking page loads on mobile.
- [ ] Services load from the booking API.
- [ ] Prices displayed on the website match the server-side service prices.
- [ ] A released appointment appears for an eligible service.
- [ ] An unreleased appointment does not appear.
- [ ] A service-restricted appointment only appears for permitted services.
- [ ] Customer can move back and forward through the booking steps.
- [ ] Required customer fields are enforced.
- [ ] Privacy Notice acknowledgement is required.
- [ ] Marketing consent is optional and stored separately.
- [ ] Successful booking produces a confirmation screen.
- [ ] Customer can add the appointment to Apple Calendar.

## 2. Booking integrity

- [ ] A slot can only be booked once.
- [ ] Two near-simultaneous booking attempts cannot both succeed for the same slot.
- [ ] A booked slot disappears from public availability.
- [ ] A cancelled booking makes its slot available again.
- [ ] A completed booking remains in the customer history.
- [ ] A booked slot cannot be deleted as availability.
- [ ] Invalid service IDs are rejected server-side.
- [ ] Invalid slot IDs are rejected server-side.
- [ ] Invalid add-on quantities are rejected/normalised safely.

## 3. Returning customer behaviour

- [ ] First booking creates one customer record.
- [ ] A later booking using the same email recognises the existing customer.
- [ ] Returning customer details are updated appropriately.
- [ ] Different email addresses do not merge customer records.
- [ ] Email matching is case-insensitive.

## 4. Infill pricing

### Builder Infill

- [ ] Qualifying completed Builder Full Set 20 days before → infill price.
- [ ] Qualifying completed Builder Full Set 21 days before → infill price.
- [ ] Qualifying completed Builder Full Set 22 days before → full-set price.
- [ ] No qualifying completed appointment → full-set price.
- [ ] Cancelled previous appointment does not qualify.
- [ ] A future previous appointment does not qualify.

### Builder & Gel Polish Infill

- [ ] Qualifying completed Builder & Gel Polish Full Set 20 days before → infill price.
- [ ] Qualifying completed Builder & Gel Polish Full Set 21 days before → infill price.
- [ ] Qualifying completed Builder & Gel Polish Full Set 22 days before → full-set price.
- [ ] No qualifying completed appointment → full-set price.
- [ ] Cancelled previous appointment does not qualify.
- [ ] A future previous appointment does not qualify.

## 5. Admin

- [ ] Correct admin credentials log in.
- [ ] Incorrect credentials are rejected.
- [ ] Admin session expires as expected.
- [ ] Protected endpoints reject unauthenticated requests.
- [ ] Availability can be released.
- [ ] Availability can be restricted to selected services.
- [ ] Availability can be removed before booking.
- [ ] Bookings can be viewed.
- [ ] Bookings can be marked completed.
- [ ] Bookings can be cancelled.
- [ ] Cancelled slots become available again.
- [ ] Calendar feed can be generated by an authenticated admin.
- [ ] Calendar feed contains appointment information only.
- [ ] Calendar feed does not contain consultation/health information.

## 6. Boundary and date/time testing

- [ ] Same-day appointment in the past cannot be booked.
- [ ] Same-day appointment later today remains bookable.
- [ ] Tomorrow's appointment is bookable.
- [ ] Past dates do not appear in availability.
- [ ] Europe/London timezone is correct.
- [ ] British Summer Time / GMT transitions are checked.
- [ ] Calendar dates and times match the booking record.

## 7. Privacy and data minimisation

- [ ] Online booking stores only the information needed for appointment administration/customer records.
- [ ] No consultation health/allergy information is requested online.
- [ ] No consultation health/allergy information is written to D1.
- [ ] Marketing opt-in is stored independently from booking necessity.
- [ ] Privacy Notice is accessible before booking is completed.
- [ ] Privacy Notice accurately describes the live data flows.
- [ ] A retention period/process is documented before production use.
- [ ] A customer data deletion/anonymisation process is documented before production use.

## 8. Security and resilience

- [ ] Production secrets are not committed to GitHub.
- [ ] GitHub Actions uses least-privilege permissions where practical.
- [ ] Admin login has protection against repeated failed attempts.
- [ ] Calendar token is treated as a private bearer credential.
- [ ] Appropriate security headers are present.
- [ ] Database backup strategy is documented.
- [ ] Database restoration has been tested.
- [ ] Error responses do not expose secrets or internal database details.

## 9. Deployment

- [ ] Latest website deployment succeeds.
- [ ] Latest booking Worker deployment succeeds.
- [ ] Worker points to the intended D1 database.
- [ ] Production environment variables/secrets are present.
- [ ] Custom domain routes are correct.
- [ ] `/health` returns the expected healthy response.
- [ ] Public booking API is reachable from the live website.

## 10. Launch gate

The system should not be considered production-ready until all critical booking-integrity, security, privacy, backup/recovery and deployment checks are either passed or explicitly accepted as a documented v1 limitation.
